Project report · Document Cortex v0.1

Ask any document, get answers you can check

Document Cortex reads PDFs, scans, handwriting, Word files and plain text in any language, builds a book-like index of each one, and answers questions with citations to the exact section and page. A second model then checks every cited sentence against its source.

1 · The problem

Why "just ask the PDF" is hard

A language model can only read a limited amount of text at once, and it answers fluently even when it has not seen the right passage. For a long book, a scanned report or a set of handwritten notes, three things go wrong:

  • Finding: the passage that answers the question is one page out of hundreds, often worded differently from the question, sometimes in another language.
  • Reading: scans and handwriting must be turned into text first, and tables of contents, page headers and boilerplate get in the way.
  • Trusting: the reader cannot tell a correct answer from a plausible invented one unless each claim points to evidence, and someone checks that the evidence really says it.

This project started as an Ayurveda assistant over the Bhavaprakasha Nighantu (OCR, LLM extraction to JSON, a vector store and a graph). Document Cortex generalises that pipeline to any document.

2 · What industry uses today

Current approaches

Two families dominate. Retrieval (RAG) cuts the document into chunks, embeds them, and shows the model the few most similar chunks. Long context puts the whole document into a very large prompt. Research systems add structure on top of retrieval: summary trees, knowledge graphs, or a table of contents the model reasons over. The table summarises what each one publicly documents.

3 · How it works

The pipeline

Reading a document happens once, when it is added. Each question then runs a short, visible chain of steps. The web UI shows every step live, with timings, so a user can see what was searched, what was found and what was checked.

4 · What is new here

Our contributions

The document's own outline as the index

One tree builder for every format: PDF bookmarks, font-size headings, Markdown and wiki headings, RFC-style numbered sections (depth from the dots), roman-numeral chapters, or titled parts when there are no headings. Tables of contents and running page headers are removed.

RAPTOR invents a tree by clustering; PageIndex needs good headings. We use the real structure and fall back gracefully.

Index cards from a small model

Each section gets a card, written bottom-up so a chapter's card summarises its sections' cards. Cards add the words a reader would use ("dose", "side effects") that the original text may not contain.

Like Contextual Retrieval, but one card per section instead of per chunk, and cached by content hash.

Sentence-level citation check

A second, smaller model checks each cited sentence against the source it cites. If another source supports it, the citation is corrected; if none does, the sentence is flagged in the answer.

None of the systems in section 2 verify each claim after writing it.

Cross-document ranking that works

Fused search scores cannot be compared between documents, so the library ranks by absolute vector similarity and keeps a document only within a margin of the best one.

Found by testing: relevant documents score 0.85–0.88, unrelated ones 0.78–0.82.

OCR that knows when it is unsure

Tesseract runs first with automatic script detection. Unsure pages go to a vision model, which corrects Tesseract's draft instead of reading from scratch. Text that repeats itself is rejected, and the page is marked unreadable.

Measured in section 5: on blurred Hindi this beats both Tesseract and the vision model alone.

Multilingual by design

Sentence splitting understands the Devanagari danda (।) and Japanese 。; keyword search uses CJK bigrams; answers come back in the question's script. Tested on English, Hindi, Sanskrit, French, Japanese and Arabic.

Cross-language questions (English question, Hindi or Arabic text) are part of the benchmark.

A visible reasoning trace

Every step of reading and answering is shown in the UI as it happens: the outline found, cards written, what search returned and why, which key was used, and each claim's verdict.

Commercial tools show the answer and citations, not the process.

Runs free, fails over cleanly

Built for Groq's free tier: rate-limit retries, daily-quota detection, then a paid key on the same model so quality stays the same. Any OpenAI-compatible local server (LM Studio, MLX) also works.

The whole 15-document library in this report was indexed for well under a dollar.
5 · How we tested, and the results

An independent benchmark

Earlier tests were small and written by the same people who built the system. For this report we built a larger test set designed to be independent of the system:

  • Different model family. Questions were written by qwen3.8-27b (Alibaba's Qwen) from the raw section text. The system's cards and answers come from gpt-oss (OpenAI). The question writer never saw the system's cards or answers.
  • Gold answers proven by code. Every gold answer carries a quote from the document, and a script checks that the quote really is in the document.
  • Six question types: facts, numbers, questions needing two sections, document overviews, unanswerable questions (the right answer is "the document doesn't say"), and cross-language questions.
  • The hard setting. Every question is asked against the whole library of documents at once, so the system must also find the right document.
  • A baseline. Plain RAG: the same 900-character passages, vectors only, top 6, the same answer model and prompt. This isolates what the tree, cards, hybrid search and drill-down add.
  • Grading. qwen3.8-27b grades each answer as correct, partial or incorrect against the gold answer and quote. A 25-question spot-check sheet lets a person audit the grader.

5b · What the benchmark changed

Fixing the weak spots, then checking on new questions

The first run showed four weak spots. Each one was traced to a cause and fixed:

  • Overviews used the first six documents in the library instead of the one the question named. Now the named document is used, or the documents whose summary card is closest to the question.
  • Two-part questions were searched as one query, so one half won and the other half found no sources. Now a compound question is split into its parts (by simple patterns, or by the model for long "how does X relate to Y" questions), and each part gets its own sources.
  • Unanswerable questions: the answer model filled gaps from its own knowledge. The answer prompt now forbids facts that are not in the sources and asks it to say which part is not covered. The baseline uses the same prompt, so the comparison stays fair.
  • OCR on blurred scans: Tesseract was over-confident, and the vision model read Hindi worse than Tesseract. Now unsure pages are escalated at a higher bar, and the vision model corrects Tesseract's draft. We also tried image clean-up (upscale, denoise, binarise) and a script hint; both made results worse and were dropped.
  • The grader sometimes wrote its grade before its reasoning and contradicted itself. It now reasons first. Every answer, ours and the baseline's, was re-graded.

Because these fixes were made while looking at the first test set, we also wrote a held-out set of new questions on sections the first set never used, after the fixes were done.

7 · Next steps

Roadmap

  • Knowledge graph (Neo4j) for the Ayurveda corpus: herbs, properties (rasa, guna, virya), diseases and formulations as typed relations, so questions like "which bitter herbs pacify pitta?" are answered by a graph query instead of search.
  • Heavily damaged Indic scans are still unreadable by every engine we tried; try a stronger or Indic-trained OCR model (e.g. a local VLM) and real scanned pages with hand-typed ground truth.
  • Reranker: our Qwen3 reranker integration lowered accuracy (suspected prompt truncation); fix and re-test.
  • Tables and figures as first-class sections, and page-level citations inside long PDF sections.
  • Human-graded test set to calibrate the automatic grader, using the spot-check sheet.
8 · Reproduce it

Run the benchmark yourself

git clone https://github.com/Pradhumn115/document-cortex.git && cd document-cortex
pip install -e .
python3 scripts/fetch_samples.py && cortex add samples/*
python3 -m cortex.evalset generate   # questions + code-checked quotes  -> bench/eval_v1.jsonl
python3 -m cortex.evalset run        # ours + plain-RAG baseline        -> bench/results_v1.jsonl
python3 -m cortex.evalset score      # grades, summary, spot-check sheet
python3 -m cortex.evalset ocr        # OCR character error rate
